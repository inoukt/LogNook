# Hardware and diagnostic protocol plan

> This is a protocol/reference plan, not a current support matrix. For implemented paths and the latest physical evidence, see [Project Status](../PROJECT_STATUS.md) and the dated reports under `docs/hardware/`.

## Original interface targets (proposal, not current delivery order)
1. **Generic ELM327 USB**: enumerate safe serial ports, probe ELM-compatible commands and AT identity; basic reset/echo/linefeed/header configuration; check actual firmware command behavior, clone inconsistencies, available bus protocol, supported PID pages. Initially target standard CAN Mode 01 read-only; add K-line and J1850 based on measured hardware/vehicle compatibility.
2. **OBDLink SX USB**: FTDI virtual COM and STN1130-type device identification, firmware awareness and separate ST command fast path. SX manufacturer claims legislated OBD protocols including CAN, KWP, ISO9141 and J1850; do not claim Ford MS-CAN/GM SW-CAN on SX hardware.
3. **RH-02/CANable**: explicitly detect candleLight/`gs_usb` vs SLCAN firmware; show VID/PID only as detection hints (clones vary), verify capability and supported bitrate. Configure 11/29-bit receive, filters if available, high-load buffering, silent/passive mode only where firmware truly supports it, raw timestamp quality. Guide WinUSB driver setup only if enumeration requires it. Linux `SocketCAN` later. Physical breakout wiring, bus bitrates and 120-ohm termination must be technician-confirmed.
4. **Tactrix OpenPort 2.0**: the current POC implements registered 32-bit J2534 v04.04 provider discovery and explicit selection, identity, and standard Mode 01 over ISO 15765. J2534 v05.00, K-line, and other protocols remain out of scope. The vendor DLL runs only in the isolated x86 worker. The 2026-10-02 OPTA passive raw-CAN observation returned combined frame data and did not verify decoded PIDs. The active Mode 01 path has since produced live Ford samples through LogNook; see the [2026-10-09 OPTA read-rate report](../results/openport2-opta-read-batch-diagnosis-2026-10-09.md). Cross-vehicle and longer-duration validation remain separate. Tactrix describes OpenPort 2.0 as 12-V hardware; do not promise heavy-duty 24-V use.

## OpenPort 2.0 POC boundary

The 32-bit worker reads fixed SAE J1979 Mode 01 service/PID requests over J2534 ISO 15765, 11-bit CAN at 500 kbit/s. It does not expose raw transmit bytes, raw CAN monitoring, K-line, service 21/22, ECU writes, sessions, security access, or automatic provider fallback. Supported-PID discovery and signal selection use the shared catalog and sample pipeline. Multiple ECU responders are rejected because the current session model does not select an ECU. Live Ford samples and polling-rate observations were recorded in the 2026-10-09 OPTA report; they do not establish compatibility with other vehicles or an extended OEM diagnostic path.

## Vehicle protocol phases
- **A**: Generic SAE J1979 / Mode 01 supported-PID scan, selected emissions PID reading, source-ECU attribution, calculated units; VIN/Mode 09 where supported, robust multi-response handling.
- **B**: ISO-TP (ISO 15765-2) addressed sessions, UDS read-only DID 0x22 and metadata-driven decoder, session/response-pending timing, unsolicited responses, physical and functional addressing. OBD-on-UDS J1979-2 distinct from arbitrary manufacturer UDS; validate against current standards.
- **C**: KWP2000 and supported K-line variants; read-only enhanced OEM profile packs, limited to documented definitions/authorized access.
- **D**: DBC raw CAN decoding, raw frame capture and filtering; J1939 PGN/SPN plus DM views on hardware electrically suited to the target vehicle, not a blanket 24-V promise.
- **E**: Newer ZEV standard and DoIP with new compatible physical hardware; optional ODX/PDX and A2L imports if legal source files are supplied.

## Coverage is three separate claims
**Physical connection** != **protocol transport** != **decoded OEM content**. Display three checks in vehicle profiles. Generic emissions PIDs reach many brands but do not imply unrestricted access to ABS, airbag, transmission, BCM, hybrid battery, every OEM measurement or security gateway. Address protected services only with legitimate access and explicit permission, never guessed unlock secrets.

## Normal acquisition and Workbench bench mode
Normal acquisition and background polling remain measurement-only: no firmware programming, coding, DTC clearing, resets, writes, erase, session/security access, routines, or actuator control. Configured signals and OEM catalog candidates follow their existing applicability and provenance rules.

The Test Workbench is a separate expert bench/research mode. It may passively sniff raw CAN, send operator-configured CAN frames, and scan user-selected CAN-ID, Mode 21, or Mode 22 ranges, including full supported ranges. A user selects adapter, bitrate, route/ID, payload or identifier range, pacing, and repeat count, then starts or stops the operation; there are no per-request approval prompts. No operation runs on app launch or adapter connection. One serialized adapter owner handles all traffic, and exact TX/RX frames, addresses, timings, scan settings, and outcomes are saved as raw research evidence without automatic decoder or vehicle-validation promotion.

Passive capture uses the adapter's listen-only mode when the device confirms it. Active bench transmission is an explicit user-selected mode. Show whether hardware or host filtering is active; do not imply hardware filtering when it is unavailable. The CAN Workbench scope adds no firmware flashing or automatic multi-step ECU programming workflow. Raw frame transmission is experimental and is not classified as read-only merely because the frame is manually entered.

Saved `.candump.csv` reports replay through the same bounded Rust `CanAnalyzer` and retain the paired `.candump.jsonl` journal path, scan provenance, TX evidence, transport errors, and clean-close state. The census includes exact per-byte value counts; comparing two captures reports IDs present on either side and changed byte-value distributions. Diagnostic timing is paired only against request/response routes actually recorded in the journal. Reports keep the raw request/reply PDU and typed outcome, including NRC and response-pending, wrong echo, malformed data, and no-response outcomes. No standard CAN route is guessed for a capture without route evidence.

Correlation analysis accepts explicitly timestamped common-pipeline samples and uses their wall-clock timestamps to align with the capture's frame clock. It reports only Pearson correlation hypotheses, with sample source and ECU labels; it never creates a decoder, graph signal, or vehicle-validation claim. The manual trigger is owned by the serialized adapter worker, keeps a bounded pre-trigger ring, records a user mark and bounded post-trigger window, and can export that window as a paired raw CSV/JSONL clip with adapter and trigger provenance. A disarm, capture stop, or session end after a mark saves and emits the partial window with an explicit incomplete terminal reason; disarming before a mark cancels the arm. The optional DBC export contains observed message IDs and a one-bit placeholder for each nonzero-DLC message, with every placeholder labeled `UNVERIFIED`; zero-DLC messages remain listed without an out-of-bounds signal field.

RH-02/Candlelight physical status: the code path and fixtures alone do not establish device identity, Windows USB enumeration, listen-only support, bitrate operation, CAN receive/transmit, or vehicle traffic. Use current status and a dated hardware report for any observed test; do not infer vehicle compatibility from adapter discovery.

## v0.3 OEM catalog and Scion xB first probe
The desktop includes the v0.3 OEM catalog as a read-only resource. Its paged search exposes candidate definitions and provenance but does not make them normal acquisition signals. Every imported OEM definition remains `auto_request=0` until exact-profile validation. Eligible source-backed service 21/22 candidates have explicit one-shot reads on supported adapters; the retained Scion xB `21 01` experiment is not continuous polling and does not validate other candidates. Raw replies and source revisions are saved separately from the catalog. See [the Scion xB research brief](../scion-xb-2014-mode21-standalone-brief-2026-10-03.md) and [current coverage](../PROJECT_STATUS.md).

The [A30 Scion xB archive](../docs/hardware/a30/README.md) preserves independent Mode 21 and Mode 06 vehicle-level observations from the same 2014 xB. LogNook now has an A30 Bluetooth transport and selected one-shot Mode 06 tests; raw/unmapped counts remain evidence, not semantic decodes or vehicle validation. Check the current hardware report for the implemented subset.

## Connection negotiation
Keep a per-adapter safe capability cache keyed by hardware identity and firmware; keep protocol hints per vehicle/ECU but reverify each vehicle session. A priority scheduler owns requests so separate data channels cannot silently compete. Any unplug/replug generates a gap event and resync, not fictitious interpolated values.

## Real hardware questions for POC
Open hardware questions remain adapter- and vehicle-specific: verify Candlelight firmware/listen-only behavior, cover ELM clone variability, and extend sustained multi-signal tests across vehicles. Record actual firmware, drivers, responding ECU, selected signals, rates and errors in a dated report. Existing SX and OpenPort results are documented in [Project Status](../PROJECT_STATUS.md); vendor specifications alone do not establish compatibility.
