## Source-backed sequence

The minimal production handshake is now: validate USB VID/PID; open selected COM
at 115200 8-N-1; send the complete adapter-only query `STI\r`; receive and validate
its firmware reply through `>`; query STDI and STSN sequentially; then discover
generic supported PIDs with 0100 and read only selected supported Mode 01 PIDs.
A queued startup banner or empty startup prompt is tolerated before the STI reply.
A missing, malformed, or unexpected reply stops the sequence before later queries.
The production code does not wake/reset the adapter or save protocol settings.

References: [OBDLink FRPM Rev F, §§6.0, 7.2, 8.4, 15.3, 15.6](https://www.scantool.net/scantool/downloads/682/obdlink_frpm_f.pdf),
[OBDLink Windows setup](https://support.obdlink.com/support/solutions/articles/43000727094),
[ScanTool UART baud guidance](https://www.scantool.net/blog/switching-communication-baud-rate/),
[FTDI D2XX interface documentation](https://www.ftdichip.com/Support/Knowledgebase/d2xxintroduction.htm).

## Sibling OBDLink/STN request-path comparison — 2026-10-02

The PcmHammer ScanTool adapter is an implementation reference for related STN hardware: it sends CAN payloads through `STPX D:...`, bounds expected replies, and uses a 2 Mbps SX rate with echo off. Its CAN-specific path also uses PCM physical ID `7E0` and ATAT0; those settings are model/client choices, so they were measured against this Ford rather than assumed. See [PcmHammer's ScanTool adapter implementation](https://github.com/PcmHammer/PcmHammer/blob/develop/Apps/PcmLibrary/Devices/ScanToolDeviceImplementation.cs).

For the same 2 Mbps, 1 ms D2XX session and 20 RPM reads, bare `010C` at ATAT1 returned **15.31/s**; `STPX D:010C, R:1, T:250` returned **33.81/s**, with 20/20 valid. Functional header `7DF` and PCM physical header `7E0` both returned about 33/s; header-on discovery showed PCM response `7E8`. The gain therefore follows the STPX request/response-count path, not the faster UART setting.

The full STPX matrix used all 35 probed generic candidates and sequential mixes of 1, 5, 8, 16, and 24 PIDs. COM4/115,200 (echo on), COM4/2,000,000 (echo off), and D2XX/2,000,000 (echo off) all measured **33.3 aggregate responses/s**, with **100% valid replies** in each mix. The 5-PID mix refreshed each signal at about 6.7 Hz; the 24-PID mix refreshed each at about 1.39 Hz. With headers enabled, the responder was PCM `7E8`; explicit `STPX H:7DF` and `STPX H:7E0` each returned about 33.6/s for RPM. ## Combined SAE PID probe — documented before transmission

The OBDwiz 4.36.0 release notes describe “Combine SAE PID Requests” (PID stuffing), a CAN refresh optimization not covered by the earlier one-PID-per-request bench. A read-only `STPX D:010C050F110D` probe returned five verified values in a 12-byte response split over two ISO-TP frames. `R:1` truncated the response after its first frame; `R:2` captured both frames and all values. ## Production implementation update — 2026-10-02

The LogNook `ObdLinkSxAdapter` now uses the measured combined-request approach
for `ISO 15765-4 (CAN 11/500)`. It enables CAN headers, repeats supported-PID
discovery, and uses the fast path only when it identifies one standard
`7E8`–`7EF` ECU response. It derives the matching physical request ID, then groups only selected supported signals so each
response payload is at most 13 bytes. The adapter sends `STPX` with that header,
the concatenated `01<PID...>` request, a frame count of one or two, and `T:250`.
It reassembles and validates ISO-TP payloads before decoding each requested PID,
rejecting truncated, unexpected, or multiple-responder responses. Echo/header
settings are restored on disconnect or connection failure. Unsupported
protocols keep the original one-PID query path.

The code is covered by a five-PID/two-frame response fixture, a first-frame-only
truncation test, decoder tests for all 35 catalog entries, and an all-35 grouping
test (seven groups, at most two frames each). The **81.42 values/s** measurement
above remains the diagnostic harness rate; the application itself has not yet
been rerun against the vehicle after this implementation. The six additional
advertised PIDs (`01`, `15`, `19`, `34`, `38`, `41`) remain out of the scalar
picker because their seed entries need structured monitor-status or
multi-channel O2 decoding.

## Periodic Mode 01 probe — 2026-10-02

The likely command names are `STPPMA period, header, data`, `STPPMD handle`, and `STPPMC`; the official manual calls this **Periodic Messaging**, not an STMP transport. It says the current protocol must be open, the period is in milliseconds, and `STPPMC` clears all handles. The manual also warns that periodic replies may interleave with replies to manual requests. See [OBDLink FRPM, Periodic Messaging](https://www.scantool.net/scantool/downloads/678/obdlink_frpm_e.pdf).

The temporary D2XX probe used echo off at 2 Mbps, opened ISO 15765-4 with `STPO`, and verified a normal `010C` RPM response before scheduling `010C` at 100 ms and 20 ms. It also added the five known catalog PIDs (`010C`, `010D`, `0105`, `010F`, `0111`) at 100 ms each. `STPPMA` returned handles for every entry. No frames arrived on the idle UART during the three-second windows. After the 100 ms RPM schedule, one manual `010C` returned two valid RPM lines in 208.5 ms; that shows an interleaved response but does not establish how many scheduled requests the ECU answered or a sustained rate.

The 20 ms schedule caused the subsequent manual RPM read to time out; `STPPMC` initially returned `STOPPED`. A separate recovery process then received `STPPMC` → `OK`, restored `ATE1`, observed no idle stream, and verified a normal RPM response at 115,200. Schedules that completed normally were removed with `STPPMD` and followed by `STPPMC`; the interrupted handle was cleared by the recovery `STPPMC`. The 20 ms schedule is not suitable for production based on this result. Periodic-message output needs a reliable, bounded receive/stop strategy before it can be used for acquisition; no production code was changed.
