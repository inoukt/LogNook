# OBDLink SX physical connection record — 2026-10-02

## Result and scope

The SX answered complete read-only commands on both FTDI D2XX and VCP COM4 at
115200 baud, 8 data bits, no parity, one stop bit, no flow control. The corrected
`ObdLinkSxAdapter` then connected through the existing `HardwareAdapter` contract,
discovered five supported LogNook signals, read one live RPM sample, and disconnected.
This is a bounded physical test on the user's 2011 Ford Flex 3.5L EcoBoost. It is
not a sustained recording, native UI test, cross-vehicle compatibility test, or
Ford MS-CAN/enhanced diagnostic validation.

The defect was the initial handshake: LogNook waited for an unsolicited startup
banner/prompt on every COM-port open. An already-powered SX did not emit one in
these tests. Sending the adapter-only query `STI\r` established communication;
the reply ended in `>`. Every later command waited for its preceding reply prompt.
The baud used for the successful test was 115200, not the 2000000 displayed in
the user's earlier FORScan session. No USB backend change was required in LogNook.

## Earlier attempts and remaining uncertainties

- Passive waits at 115200, 38400, and 2000000 received no unsolicited banner. Some
  vehicle reconnection timing was confirmed by the user; others was not. Those
  waits did not prove the adapter was unable to answer a complete command.
- The user explicitly approved a 10 ms UART BREAK wake test. VCP and D2XX versions
  sent that pulse and saw no prompt. Recognition of the wake trigger is unknown.
  The manual says a recognized wake causes ATWS; ATWS retains the selected UART
  baud. It was incorrect to infer that a warm reset necessarily restored 115200.
- The user explicitly requested ATSP. One separate temporary D2XX test sent
  `ATSP 6\r` at 2000000 and timed out. Whether it was accepted or saved in NVM is
  unknown. The later `STPRS` reply verifies the current CAN 11/500 protocol only;
  it does not prove that earlier NVM write occurred. It was not repeated.
- No bare CR, DTC-clear request, ECU write, actuator request, OEM/UDS request,
  firmware update, or factory reset was sent by these tests.
- One initial D2XX open returned DEVICE_NOT_OPENED. Enumerating devices showed the
  SX with port_open=false; a subsequent open succeeded. Enumeration and timing were
  not isolated as separate causes, so no general driver defect is claimed.
- D2XX reported a 16 ms latency timer. It was read, not changed. Its effect on
  sustained acquisition has not been measured. LogNook retains the simpler VCP
  transport, which now works through its existing contract.

## Source-backed sequence

The minimal production handshake is now: validate USB VID/PID; open selected COM
at 115200 8-N-1; send the complete adapter-only query `STI\r`; receive and validate
its firmware reply through `>`; query STDI and STSN sequentially; then discover
generic supported PIDs with 0100 and read only selected supported Mode 01 PIDs.
A queued startup banner or empty startup prompt is tolerated before the STI reply.
A missing, malformed, or unexpected reply stops the sequence before later queries.
The production code does not wake/reset the adapter or save protocol settings.

References: [OBDLink FRPM Rev F, §§6.0, 7.2, 8.4, 15.3, 15.6](https://www.scantool.net/scantool/downloads/682/obdlink_frpm_f.pdf),
[OBDLink Windows setup](https://support.obdlink.com/support/solutions/articles/43000727094),
[ScanTool UART baud guidance](https://www.scantool.net/blog/switching-communication-baud-rate/),
[FTDI D2XX interface documentation](https://www.ftdichip.com/Support/Knowledgebase/d2xxintroduction.htm).
