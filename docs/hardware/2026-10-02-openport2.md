# OpenPort 2.0 connection test — 2026-10-02

## Implementation update — 2026-10-04

LogNook now has a separate 32-bit J2534 v04.04 worker, typed bounded IPC, a core `OpenPort2Adapter`, and Tauri/UI provider selection. It supports only read-only standard Mode 01 over ISO 15765 at 500 kbit/s; supported signals and measurements use the shared acquisition/recording/graph pipeline. The worker accepts only explicitly selected registered Tactrix/OpenPort/OPTA providers and loads their existing registered DLLs. Its ISO15765 channel uses per-responder flow-control filters, skips J2534 transmit confirmations, and keeps partial replies returned with a timeout. It does not transmit the raw-CAN sniff messages described in the historical passive probe, and it has no service 21/22 path.

Software verification covered provider filtering and cleanup, bounded IPC, PID support pages, ECU identity checks, timeout cleanup, decoded samples, and the common engine pipeline. The x86 MSVC worker builds successfully. During implementation, the current development host's provider-list query returned no matching registered provider, so no adapter DLL was loaded and no physical vehicle diagnostic request was sent. The earlier 2026-10-02 inventory below records Tactrix and OPTA registrations on the test PC; provider availability is machine-specific. Those OPTA identity/passive-CAN observations remain historical evidence and do not verify the new active Mode 01 path.

On the test PC, from `apps/desktop`, run `npm run build:j2534-worker` and `npm run tauri dev`. Select **OpenPort 2**, choose the existing registered OPTA provider, press **Identify**, then **Connect**. Record the provider and API version, supported PIDs, responding ECU, raw PID response, latency, sample rate, and errors. ## Scope and physical state

The user requested an OpenPort 2 test and confirmed USB to this PC and OBD to the
Ford. Windows inventory and adapter identification were followed by one bounded,
passive diagnostic attempt. This temporary harness is not an implemented LogNook
J2534 backend.

## Documented sequence before execution

1. Inspect USB `0403:CC4D`, driver properties, J2534 registry entries, DLL version,
   signature and PE architecture. Do not change the installed driver.
2. Load the registered Tactrix `C:\Windows\SysWOW64\op20pt32.dll` in a separate
   x86 process. The installed header uses Windows `__stdcall` and 32-bit longs.
3. Call `PassThruIoctl(0, 0x70004, NULL, wchar_t[512])`, Tactrix's documented
   `TX_IOCTL_GET_DEVICE_INSTANCES`. Stop if it cannot find an available device.
4. If present, call `PassThruOpen(NULL, &device_id)`, then
   `PassThruReadVersion(device_id, firmware, dll, api)`, with 512-byte buffers.
   Always `PassThruClose` after a successful open. No channel in this first test.
5. Only after successful identification, a separate bounded passive test may use
   the installed vendor CAN logger's sequence: `PassThruConnect` with protocol
   CAN (5), `SNIFF_MODE | CAN_ID_BOTH` (`0x10000800`), 500000 bit/s; a
   `PASS_FILTER` with a zero mask/pattern; `PassThruReadMsgs` for five seconds;
   then `PassThruDisconnect` and `PassThruClose`. Abort on an unsupported flag;
   never fall back to ordinary CAN. The Ford's 500 kbit/s rate was confirmed in
   the prior SX test. Sniffing produces raw transport evidence, not decoded PIDs.

The harness has no transmit, periodic-message, programming-voltage, reset,
firmware-update, K-line-init or ECU-write calls. `PassThruGetLastError` is used
only to report failures. No bus protocol or bitrate scan is planned.

### Actual adapter test

Compiled [the bounded x86 identity probe](probes/openport2_identity.cpp) using the
installed MSVC tools, then ran it once. [Raw output](openport2-identity.log):

```text
DLL: C:\Windows\SysWOW64\op20pt32.dll; process: x86
TX_IOCTL_GET_DEVICE_INSTANCES: 0x00000008
PassThruGetLastError: 0x00000000,
```

`0x08` is `ERR_DEVICE_NOT_CONNECTED` in the installed vendor header. The probe
exited 2 at the presence query. `PassThruOpen`, `PassThruReadVersion` and the
passive channel test were **not executed**. No vehicle channel was opened or
vehicle message sent. The DLL loaded successfully and the probe exited cleanly.

The driver mismatch is a supported explanation: `oem458.inf` explicitly calls
itself a WinUSB replacement, uses the WINUSB service and interface GUID
`{C2E6EBE6-2FC5-4781-A4E5-B993B37CB069}`. The installed Tactrix INF uses class
VehiclePassThru and service `openport`, with driver version `1.0.0.4227`, dated
2014-04-07. This test does not establish that the hardware is faulty, nor prove
the driver is the sole cause. Driver restoration followed by the same presence
query would test that explanation. No driver was replaced and OPTA was not used
as an implicit fallback.

```powershell
Get-PnpDevice -PresentOnly | Where-Object {

foreach ($registryPath in @(
  'HKLM:\SOFTWARE\PassThruSupport.04.04',
  'HKLM:\SOFTWARE\WOW6432Node\PassThruSupport.04.04',
  'HKLM:\SOFTWARE\PassThruSupport.05.00',

$openportInstance = 'USB\VID_0403&PID_CC4D\TAO$BYMP'
Get-PnpDeviceProperty -InstanceId $openportInstance | Where-Object {
  $_.KeyName -match 'HardwareIds|DriverVersion|DriverProvider|DriverInfPath|Service|BusReportedDeviceDesc'

  $_.DeviceID -eq $openportInstance

Get-CimInstance Win32_PnPEntity -Filter "PNPDeviceID LIKE 'USB%VID_0403%PID_CC4D%'" |
  Select-Object Name,PNPDeviceID,Status,Service,HardwareID | ConvertTo-Json -Depth 3

foreach ($dllPath in @(

  'C:\Program Files (x86)\OPTA\Tactrix\opta_j2534_0404_tactrix.dll'
```

### Bounded identification sequence documented before execution

Load the installed OPTA DLL explicitly in the same isolated x86 harness, using
`--opta`. Do not use Tactrix's vendor-specific presence IOCTL: OPTA's shim does
not implement it. Call `PassThruOpen`, `PassThruReadVersion`, then always
`PassThruClose` after a successful open. These standard API signatures match the
installed header. No vehicle channel or message API is loaded by this probe.

The reviewed source implements open by USB `ati\r\n` (identify) and
`ata\r\n` (attach), version by returning cached identity, and close by
`atz\r\n` (detach). These are adapter-control transfers, not OBD/ECU messages.
No firmware updater, bus initialization or programming-voltage call is used.
Capture the DLL's trace for this probe to compare observed USB behavior with the
reviewed source. The user can leave ignition off for identification.

### Passive compatibility review

The reviewed OPTA connect code forwards channel flags to firmware using `ato`,
and raw CAN reads return transport frames. The official Tactrix `SNIFF_MODE`
definition therefore remains a candidate, but current source review alone does
not establish the installed binary's behavior. Verify identity and wire trace
first; never fall back to active CAN if a sniff-mode test is rejected. Request
ignition ON / engine OFF only when the bounded passive test is ready.

### Passive test prepared before execution

The same probe's explicit `--opta-passive` mode verifies the known firmware/API,
then loads connect, disconnect, PASS-filter and read functions only. It requests
CAN5, flags `0x10000800`, 500000 bit/s, zero 4-byte CAN-ID mask/pattern, TxFlags0,
and no flow-control message. Reads have 100 ms timeouts and a five-second outer
deadline. Missing functions, rejected connection/filter, malformed metadata or
unexpected transmit status stop the test. Successful channel opens are always
disconnected before closing. There is no ordinary-CAN fallback or transmit
function binding.

MSVC `/W4` compilation passed with no emitted warnings. A Luna sub-agent
independently reviewed the source and installed vendor definitions without
touching hardware or files. It confirmed the flag forwarding and warned that
the older installed OPTA binary may force raw-filter padding `0x40`. Record the
actual `atf` wire flags and treat an empty capture as inconclusive. A returned
sniff flag/trace does not independently measure electrical silence.

The user was instructed to turn ignition ON, engine OFF only after this probe
was ready and replied “ready”. The documented five-second target must not be
represented as decoded PID acquisition or a sustained rate.

### Actual passive result and compatibility limit

Ran once with `--opta-passive`, ignition ON / engine OFF. Identity, CAN connect,
PASS filter, first read, disconnect and close all returned `0x00000000`.
The receive guard stopped after **109 ms**, before the five-second target:
`Unexpected frame metadata: stopping`. Probe exit was 4; no malformed result
was accepted as a raw frame. The rejection did not print the full metadata,
so its exact returned DataSize/RxStatus are unavailable. It was not retried and
the bounds were not relaxed.

[Host output](openport2-opta-passive.log), [USB/API trace](openport2-opta-passive-wire.log)
and [a small physical fixture](fixtures/openport2-opta-ford-can.json) retain the
evidence. The trace shows **104 Normal CAN frames across 24 IDs**, including
0x047, 0x169, 0x200 and 0x430. This count includes frames consumed while awaiting
disconnect acknowledgement. Adapter timestamps run from 1407567063 through
1408001605 microseconds. It is not a five-second capture or rate measurement.

The installed DLL's raw API result visibly combines frames: the first parsed
wire frame is ID0x169 with payload `41 00 00 00 00 00 00 00`; the next is ID0x200
with payload `2E 61 28 F8 28 F8 20 00`. The shim logs one returned message whose
prefix is `00 00 01 69 41 00 00 00 00 00 00 00 2E 61 28 F8`: the next frame's
data follows the first frame, losing its ID boundary in the returned result.
This behavior is consistent with the reviewed source's older CAN reassembly
path, but the DLL's exact source build is unknown. The pinned source revision
also contains a separate raw-CAN per-frame path; that does not establish which
path the installed binary contains. Do not try to recover ECU
addresses/timestamps by guessing boundaries in this ABI result.

After the physical test, the Luna reviewer also checked
[June 3 source at commit `282a4af0316eee40dc6a48c78fbc1525dfc2b7ad`](https://github.com/MCU-Innovations/opta-j2534-rs/blob/282a4af0316eee40dc6a48c78fbc1525dfc2b7ad/j2534-core/src/devices/tactrix/mod.rs#L481-L541).
That revision already contains the raw per-frame path. Its presence does not
identify the installed DLL's build or establish that it was field-tested.

Actual adapter-control TX was exactly:

```text
ati\r\n
ata\r\n
ato5 268437504 500000 0\r\n
atf5 1 64 4\r\n + 4 zero mask bytes + 4 zero pattern bytes
atc5\r\n
atz\r\n
```

`ato` preserves the requested sniff flag (`0x10000800`). The installed DLL
changes raw-filter TxFlags from requested 0 to **64 (0x40)**. CAN reception was
nevertheless observed; the capture does not establish that padding suppressed
traffic. There was no `att` transmit command, flow-control filter, diagnostic
request, pin-voltage change or firmware updater. Sniff-mode behavior is supported
by the documented flag and observed control trace; electrical silence was not
independently measured with another analyzer.

The user was told the test had closed and could turn the key OFF. The USB binding
and installed DLL remain unchanged. **USB identification and Ford CAN reception
are verified; reliable raw frames through this installed OPTA ABI are not.**
