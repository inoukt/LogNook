## P1 — Transient bus errors end the whole acquisition session

**Where:** `crates/lognook-core/src/acquisition.rs:72-84` (`run()`), with
`crates/lognook-core/src/obdlink_sx/serial.rs:11` (2 s response timeout) and
`crates/lognook-core/src/obdlink_sx_protocol.rs:340` (range check).

Any `read_samples` error — one `> prompt` timeout, one malformed frame, one out-of-range decode —
sets `failed = true`, sends `Error` + `Disconnected`, and stops the worker. There is no retry or
consecutive-failure threshold. On a live CAN bus, single timeouts and partial responses are normal
events; today each one costs the user their whole session and live view.

**Suggested fix:** retry a bounded number of times per cycle with a short backoff; only tear down
after N consecutive failures (or on an unrecoverable serial I/O error). Out-of-range decoded values
are better represented as a non-`Valid` quality/skip for that signal than as a session-ending error.
*(Note: `SampleQuality::Stale` already exists in the model but no producer emits it — see the
2026-10-05 main re-check report.)*

## P2 — OpenPort 2 read timeout kills the worker, and reads are one round-trip per PID

**Where:** `crates/lognook-core/src/openport2/worker_client.rs:15,90,~128-135` and
`crates/lognook-core/src/openport2.rs:168` (`read_pid`).

Every `ReadMode01` request gets a 1 s timeout (`SHORT_TIMEOUT`). On timeout the client **kills the
worker process** (`terminate()`), which propagates as a read error, which — per P1 — ends the
session. A single slow/multi-frame PID answer (or a busy ECU) therefore tears down the adapter.

Second aspect: `read_samples` issues **one JSON request and one J2534 exchange per unique PID**
sequentially, so per-signal rate degrades as 1/(PID count × latency). The SX path already solves
this with grouped stuffing (`STPX` with several PIDs); the worker protocol has no equivalent.

**Suggested fix:** raise/parameterise the read timeout; retry a timed-out PID or mark it failed
rather than killing the worker; add a batched `ReadMode01 { pids: Vec<u8> }` request so the worker
can stuff or sequence several PIDs inside one round-trip.

## P2 — Sample queue backpressure blocks the acquisition thread (and `stop()`)

**Where:** `crates/lognook-core/src/pipeline.rs:18,47,105` (`QUEUE_CAPACITY = 256`,
`SyncSender::send`).

The acquisition thread blocks when the pipeline queue is full. If the consumer stalls (disk stall
during recording, suspended event sink), serial polling stops while samples pile up; `stop()` then
`join()`s the worker, so Disconnect waits for the backlog to drain instead of cancelling. In the
worst case the UI appears hung exactly when a user is trying to stop a misbehaving session.

**Suggested fix:** for live samples either send with a deadline and surface a "pipeline saturated"
condition, or drop/mark rather than block with a visible counter; consider decoupling recording
writes from the pipeline thread (the writer is synchronous per sample).
*(Trade-off note: blocking is lossless, so this is a deliberate-versus-real-time decision, not
strictly a defect.)*

## P3 — Negative OBD responses are reported as "no response"

**Where:** `crates/lognook-core/src/obdlink_sx_protocol.rs:47,74` (`parse_mode01_responses`).

A `7F 01 12` style negative response (service not supported, conditions not correct, busy — the
responses a real ECU sends for the six "review-required" PIDs) is never recognised; the user sees
`No response for Mode 01 PID XX`, which misdiagnoses a valid ECU answer as a dead link.

**Suggested fix:** detect `7F <service> <NRC>` (both the ISO-TP and legacy text paths) and return
the NRC with its standard meaning.

## P3 — An unexpected PID in a stuffed response aborts the group

**Where:** `crates/lognook-core/src/obdlink_sx_protocol.rs:~100-115`
(`parse_mode01_payload_for_service`).

The parser walks the combined payload and returns an error for the first PID whose data width is
unknown. If an ECU volunteers additional PIDs beyond those requested (permitted by J1979), the
group fails, and per P1 the session ends. Only the requested PID's bytes are needed.

**Suggested fix:** stop parsing at the first unknown PID if the requested PID has already been
found; error only when it cannot be located.

## P3 — Windows console window flashes when the J2534 worker starts

**Where:** `crates/lognook-core/src/openport2/worker_client.rs:34` (`Command::new(worker_path)`).

The worker is a console executable spawned from a GUI process with no creation flags, so Windows
may briefly show a console window on connect/provider listing.

**Suggested fix:** on Windows spawn with `CREATE_NO_WINDOW` (`creation_flags(0x0800_0000)`).

## P3 — Build recipe no longer configures a working Rust toolchain on this host

**Where:** `PROJECT_STATUS.md` build recipe (`call X:\VS\Common7\Tools\VsDevCmd.bat ...`).

On this machine `VsDevCmd.bat` prints its banner but sets neither `PATH` for `cargo` nor the MSVC
`LIB`/`INCLUDE` (it reports `'vswhere.exe' is not recognized`; `cl`/`link` are not found
afterwards). Tests were run successfully with:

- `PATH` prepended with `X:\VS\VC\Tools\MSVC\14.51.36231\bin\Hostx64\x64` and `X:\Cargo\LogNook\bin`
- `LIB`/`INCLUDE` pointing at that MSVC version plus Windows Kits `10.0.26100.0`
  (`ucrt\x64`, `um\x64`, and the matching `Include` dirs)

**Suggested fix:** pin this explicit environment in the documented recipe (or restore
`vswhere.exe`/register the VS instance so `VsDevCmd` works) — otherwise the "documented" test
command silently doesn't work on this host.

## Notes (intentional behaviours seen while auditing)

- A single non-finite live sample fails the active recording (`pipeline_worker.rs:44-58`), and a
  test pins that policy (`invalid_sample_stops_recording_and_keeps_partial_session_readable`). It is
  deliberate, but it means one bad adapter frame ends a recording the user may still want; worth a
  product decision.
- FORScan wide-CSV import anchors `wall_time_unix_ns` to import time and marks samples
  `origin: Live` (`csv_io.rs` FORScan path). Both are documented in code; only the "Live" label is
  potentially confusing in exports/filters.
- The SX grouped path assumes `STPX R:` equals the ISO-TP frame count; hardware runs recorded in
  `PROJECT_STATUS.md` (350/350 valid groups) cover the 1–2 frame cases the grouping allows.
